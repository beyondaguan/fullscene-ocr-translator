## 一、这项目干吗的（问题定义）

### 1.1 一句话

**一个 Windows 单机工具：对屏幕上任意内容（整屏 / 框选区域 / 本地图片 / 剪贴板文本）做 OCR 识别并翻译成中文，结果回填到主窗体，支持历史记录与 AI 对话。**

### 1.2 要解决的问题

| 痛点 | 现状（用户场景） | 本项目方案 |
|------|----------------|-----------|
| 看外文截图/PDF/视频/游戏画面要逐字敲进翻译器 | 手动复制 → 开浏览器 → 粘贴 → 翻译，来回切换 | 快捷键一键截图 → OCR → 翻译 → 回填主窗体 |
| 只想要画面一小块文字，不想整屏 | 无轻量工具 | 框选区域翻译：全屏遮罩 → 拖框 → 仅识别框内 |
| 剪贴板里的外文文本 | 手动开翻译器 | `Ctrl+V` 直接粘贴翻译 |
| 翻译历史无法追溯 | 无记录 | SQLite 历史库，可查看/清空 |
| 翻译结果想听发音 | 无 | TTS 朗读译文 |
| 希望用不同翻译引擎 | 绑定单一厂商 | 引擎 trait + registry（azure/google/local_llm/mymemory/openai_compat） |

### 1.3 非目标（明确不做）

- 不做公网部署、多用户认证、云同步。
- 不做重型插件运行时（T3 进程外插件暂缓）。
- 不做 SaaS。
- 当前仅 Windows 10/11 x64 单机为目标平台（macOS/Linux 为远期目标态，未验证）。

### 1.4 竞品定位（决策背景）

- **Pot**（19.4k star）2026-09 归档转只读，用户观望替代品 → 本项目窗口期打开。
- Pot 技术栈 = Tauri + Rust，常驻 ~80MB，本地 HTTP API 供外部调用 → 验证本项目 Tauri 2 选型。
- 本项目定位：**轻量单机 + 全场景 OCR + 本地知识**，对标 Snow Shot / Manggo / Pot / TTime。

## 四、如何实现（架构）

### 4.1 容器视图（当前实际）

```
┌──────────────────┐   Tauri 2（tao 窗口 + wry/WebView2）   ┌─────────────────┐
│  shared-ui React  │ ─────── window.__TAURI__.core.invoke ──► │  fs-gui         │
│  AppShell         │ ◄─────── event.listen(translation-ready)  │  commands.rs    │
└──────────────────┘                                        └────────┬────────┘
                                                                     │
┌──────────────────┐    Native Messaging（注册已自动化，桥接待真机验证）      ┌────────────▼────────┐
│ extension/       │ ────────── stdio ──────────────► │ fs-host             │
│ 浏览器扩展（三模式已实现）│                                  │ NM桥+dispatch        │
└──────────────────┘                                  └────────┬────────────┘
                                                               │
                                                     ┌─────────▼─────────────┐
                                                     │ fs-core（核心业务库）     │
                                                     │ OCR/翻译/历史/配置/热键   │
                                                     └───┬────┬────┬────┬────┘
                                                         │    │    │    │
                                                   SQLite  LLM  云API  模型文件
```

依赖方向（目标态）：`host/gui → core → platform`。当前 `core` 仍直接依赖 `windows` crate（G1 断点，见 §五）。

### 4.2 窗口创建机制（实体窗口）

| 窗口 | 创建方式 | 关键配置 |
|------|---------|---------|
| 主窗体 | `tauri.conf.json` `app.windows[0]` 声明，Tauri 运行时用 tao 创建 | 960×640，min 720×480，decorations，center |

- **桥接方案**：`withGlobalTauri: true` 已启用（ADR-005 Accepted），`window.__TAURI__` 正常注入，前端 `invoke` 可用。**注意**：切勿再与 `initialization_script` / `set_focus()` 组合使用（曾触发 `0xcfffffff`，见 ADR-005）。

### 4.3 窗口内操作链路（桥接）

```
用户点击按钮 / 按快捷键
  → React 事件（AppShell onAction / useHotkey）
  → useNativeMsg.invoke(cmd, args)
  → window.__TAURI__.core.invoke(cmd, args)     ← 依赖全局注入
  → fs-gui commands.rs 的 #[tauri::command]
  → fs-core 业务逻辑
  → 结果返回 Promise / 事件回传
```

`useNativeMsg.ts` 当前暴露的桥接方法（与 `commands.rs` 一一对应）：

| 前端方法 | Rust 命令 | 说明 |
|---------|----------|------|
| `getConfig()` | `get_config` | 读取配置 |
| `saveConfig(config)` | `save_config` | 保存配置（热键热重载） |
| `getStatus()` | `get_status` | 状态（ocr_ready 等） |
| `ping()` | `ping` | 连通性 |
| `listEngines()` | `list_engines` | 引擎列表 |
| `testEngine(id, text)` | `test_engine` | 测试引擎 |
| `translateText(text, src, dst)` | `translate_text` | 文本翻译 |
| `screenshotTranslate(src, dst)` | `screenshot_translate` | 整屏截图翻译 |
| `getHistory(limit)` | `get_history` | 历史 |
| `clearHistory()` | `clear_history` | 清空历史 |

### 4.4 整屏截图翻译数据流

1. 触发：窗口内 `Alt+1` / 按钮 / 窗口外 `Ctrl+Alt+O`。
2. `screenshot_translate` → `fs-core::screenshot::capture_target(CaptureTarget::Active)`（GDI BitBlt/GetDIBits，BGRA）。
3. OCR（oar-ocr 0.9，PP-OCRv6）→ 文本。
4. 翻译路由（engine registry）→ 译文。
5. 回填前端（invoke 返回 / `translation-ready` 事件）。

### 4.5 框选区域翻译数据流（已下线）

2026-10-03 整体移除（见版本历史 1.26）。原链路为：窗口内 `Alt+2` / 窗口外 `Alt+Q` → `open_selection` 创建全屏透明遮罩 → 拖框 → `selection_done(region)` → `capture_target(Region)` → OCR/翻译回填。

移除原因：遮罩依赖「全屏 + 透明 + 无边框 + 置顶」窗口，在本机 WebView2 下从未真机验证通过，且为真机崩溃源之一。`CaptureTarget::Region` 与 `screenshot::capture` 的矩形分支仍保留在 `fs-core`（纯数据层，无窗口依赖），将来若重启框选可直接复用。

### 5.3 关键工程事实（踩过的坑，必须遵守）

| 事实 | 说明 |
|------|------|
| 扩展真机 E2E 三坑 | ① `browser.close()`（Playwright connectOverCDP）会把**整台 Edge 关掉**，收尾只能直接 `process.exit`；② **必须每轮全新 profile**，复用旧 profile 时 Edge 不再加载 `--load-extension` 的扩展；③ 后台进程要用 `spawn(detached)`/后台任务启动，否则随 shell 结束被回收。另：探测元素类名要写准——错误提示条的 class 是 `fullscene-tooltip` 且 **8 秒后自毁**，探测必须早于它消失。 |
| 扩展网络调用必须带超时 | 真机教训：`fetch` 无 `signal` 时，代理/墙内环境下会**永久 pending**，前端表现是「点了没反应」（无结果、无报错）。所有引擎 fetch 必须有超时；`engine-router` 用 `withTimeout` 给单引擎（12s）、`available()` 探活（12s）、整条降级链（20s）封顶，保证一定落地为成功或可见错误。 |
| 引擎注册不能只靠 init() | MV3 Service Worker 随时回收重启，`init()` 内有 await/try 分支；`registerDefaultEngines()` 必须放在 background **模块顶层**（幂等），否则真机会抛「没有可用的翻译引擎」。 |
| MSVC link.exe 遮蔽 | Git-bash coreutils `link.exe` 遮蔽 MSVC `link.exe`，裸 shell 无 LIB/INCLUDE → `LNK1181 kernel32.lib`。解法：`source scripts/msvc-env.sh`（或重启后继承已持久化的用户 PATH/LIB/INCLUDE）。 |
| D 盘 pnpm symlink | `pnpm install` 报 `os error 2` → `pnpm-workspace.yaml` 已配 `nodeLinker: hoisted`，勿删。 |
| npm 网络全挂 | 残留失效代理（31180/31181）导致全部请求失败；`~/.npmrc` 只留 registry 镜像 + `strict-ssl=false`。 |
| dev:ui 必须起 dev server | `tauri.conf.json` 的 `build.devUrl=http://localhost:1420`，所以 `dev:ui` 只能是 `pnpm --filter shared-ui dev`（vite dev server，1420 strictPort），**不能**用 `build:watch`（只产 dist、不起服务 → Tauri dev 白屏）。曾写错，2026-09-30 修正。 |
| 验证 GUI 时 PowerShell 工具的两个坑 | ① `Add-Type -AssemblyName` 被安全策略拦截（"compiles and loads .NET code at runtime"）→ 截屏改用**系统 Python** 的 Pillow（`C:\\Users\\Administrator\\AppData\\Local\\Programs\\Python\\Python313\\python.exe`，有 PIL 12.2；托管版 3.13.12 无 PIL）；② PowerShell 工具的 stdout 不回传（只显示 exit code）→ 查进程/窗口标题用 `tasklist /v /fi "imagename eq fs-gui.exe"`，拿 hwnd 用 `user32.FindWindowW`。 |
| tauri dev 前端未起 | 无 `beforeDevCommand`，须先 `pnpm --filter @fullscene/shared-ui dev`（1420 strictPort）再 `pnpm --filter gui tauri dev`。 |
| `crates/gui/node_modules/@tauri-apps` 空目录 | 手动建 junction：`New-Item -ItemType Junction -Path crates\gui\node_modules\@tauri-apps -Target node_modules\@tauri-apps`。 |
| WebView2 缓存损坏 | `%LOCALAPPDATA%\com.fullscene.ocr\EBWebView` 损坏会导致 `0xcfffffff`，清缓存可解。 |
| 模型文件必须在「exe 同目录」或「CWD 相对目录」 | `ocr_models::load_models(None)` 的解析顺序是 ① exe 自身目录下 `models/ppocrv6` ② 相对 CWD 的 `models/ppocrv6`。所以 `cargo test -p fs-core` 的 CWD **不保证**是 crate 根——测试里一律用 `env!("CARGO_MANIFEST_DIR")` 定位（见 `ocr.rs` 的 e2e 测试）。GUI/发布态必须把模型放到 exe 旁的 `models/ppocrv6`。 |
| 模型下载源与速度 | 官方 Release 在 GitHub：直连实测仅 **~136 KB/s**（small 三件套 30MB 需约 4 分钟）；`paddleocr.bj.bcebos.com` 200 可达、`modelscope.cn` 302 可达、**`huggingface.co` 完全不可达（000）**。已提供多镜像回退脚本：`bash scripts/fetch_ocr_models.sh [tiny\|small\|medium]`（依次尝试 ghfast.top / gh-proxy.com / ghproxy.net / 直连）。 |

| 划词/悬停翻译「不触发」 | 根因常是**没有可用引擎**：默认 MyMemory 免费额度耗尽（返回 `YOU USED ALL AVAILABLE FREE TRANSLATIONS FOR TODAY`），且未配置 SiliconFlow/OpenAI API Key → `selectEngine` 抛「没有可用的翻译引擎」。已新增**微软翻译引擎**（免密钥，Bing `ttranslatev3`）为默认主引擎，划词/悬停即可用，不再依赖第三方密钥。若仍不触发：确认加载的是 `extension/dist` 且已在 `edge://extensions` 点「重新加载」。 |
| 划词「译」按钮：不要依赖 click / 不要在选区形成时高亮（**1.21 架构级约束**） | 1.20 用「mousedown 置位 + onSelect target 判断」抑制，真实浏览器仍被击穿（原文抖动 + 按钮跳位 + 无结果）。**三条硬约束**：① **翻译必须在 \`mousedown\` 触发**，绝不等 \`click\`——按钮被中途移除、页面脚本拦截事件都会让 click 永不触发；② btn 的 \`mouseup\` 必须 \`stopPropagation()\`，让 \`onSelect\` 根本收不到（否则重建按钮 + 重复高亮）；③ **\`highlightRange()\` 只能在翻译成功后调用**——它用 \`<mark>\` 包裹选区，会改 DOM（原文视觉抖动）并**销毁用户刚划出的选区**。此外失败路径必须经 \`deps.onError\` 给可见提示（main.ts 3 秒节流），否则用户只看到"点了没反应"。按钮回调用 \`runTranslate\`（立即）而非 \`debouncedTranslate\`（带防抖）。 |
| 划词「译」按钮点击后跑掉/不翻译（**1.20 修正根因**） | 真实根因是**事件时序**：`mouseup` 早于 `click` 触发。① 若抑制标记只在 `click` 里置位，则拦不住 `mouseup` 阶段的 `onSelect`——`onSelect` 会走 `hideSelectionButton()` + 重建按钮，使**正在被点击的按钮从 DOM 消失 → click 永不触发 → 翻译根本没被调用**；② `document` 上的 `mousedown/scroll` 监听靠 `btn.addEventListener('remove', ...)` 清理，但 **DOM 标准没有 `remove` 事件**，监听器只增不减，累积后旧闭包会在 mousedown 捕获阶段把"当前按钮"误删，同样让 click 丢失。解法：① **在 `mousedown` 阶段就置位** `lastButtonClickAt`（早于 mouseup），并在 `onSelect` 首行加 `target` 判断（mouseup 落在按钮上直接 return），`click` 里再清零（只抑制本次点击的 mouseup，不误伤后续划词）；② document 监听器句柄提到模块级，统一在 `hideSelectionButton()` 里移除；③ 按钮点击**直接翻译**，不再走 250ms 防抖（用户点了就该立即响应）。回归测试见 `tests/selection-button-click.test.ts`（真实派发 mousedown→mouseup→click）。 |
| 设置页「应用并保存」按了没反应（**1.32 修正根因**） | 三层问题叠加：① **前端吞异常**——`main.tsx` 的 `saveConfig` catch 里只 `setError(String(e))` **不 rethrow**，而设置页 `onClick={() => onSave?.(cfg)}` 不 await/catch，失败被完全吞掉；② **错误提示渲染错位置**——`error` prop 只传给了工作区 `Workspace`，`Settings.tsx` 里**从未使用过 `error`**，设置页自身零提示；③ **`update_config` 会重建 OCR 引擎**（`ocr::build_engine(...)?` 带 `?`），任何加载失败都让整个保存失败，而该函数**一行日志都没有**。解法：`saveConfig` 失败时 rethrow；`Settings` 新增 `doSave()` 自行 try/catch 并就地显示成功/失败（含失败原因），新增 `error` prop 渲染主程序错误；`update_config`/`save_config` 补 `crate::log::line` 留痕。 |
| 全局热键注册失败无任何线索（**1.32 修正根因**） | `fs-core/src/hotkey.rs` 三处告警（`RegisterHotKey` 失败 / 回调 panic / 线程未就绪）全用 `eprintln!`，而 **fs-gui 是 windows 子系统程序、没有控制台**，`eprintln!` 输出无人可见。真机表现就是「热键按了没反应」且零线索（`Ctrl+Alt+E` 不生效即此）。解法：新增 `spawn_hotkey_loop_with_warn(actions, on_warn)`，把告警回调注入；`fs-gui` 侧传 `\|msg\| crate::log::line(...)` 写进 `%APPDATA%/FullSceneOCR/logs/fs-gui.log`。原 `spawn_hotkey_loop` 保留为薄封装（默认仍 `eprintln!`），**不影响 fs-core 独立使用与既有单测**。告警回调需在「线程内两处 + 主线程一处」共用，`impl Fn` 不可 clone，必须用 `Arc` 共享。 |
| 设置页看不到 `Ctrl+Alt+E` / 无法配置（**1.32 修正根因**） | **前后端热键表不同步**：Rust `config::DEFAULT_HOTKEYS`（`config.rs:30-32`）有 3 项（含 `cycle_engine` = `Ctrl+Alt+E`），但前端 `Settings.tsx` 的 `GLOBAL_HOTKEY_ACTIONS` 只有 2 项 → 该动作既不显示也不可改，用户只能吃代码默认值。解法：前端补第三项并加注释要求**与 Rust `DEFAULT_HOTKEYS` 逐项对齐**。同类不同步风险：新增引擎/热键时必须两侧同时改。 |
| 降级链「链外兜底」会让离线引擎抢先选中 + 默认链缺 argos（**1.32 修正根因**） | ① **默认链不含 argos**：`TranslateConfig::default()`（`config.rs:80`）与前端 `Settings.tsx` 的 `DEFAULT_ORDER` 都只有 3 项 → argos 连设置页降级链列表都不出现，用户无法启用；② **`select()` 有链外兜底**：`registry.rs:50-53` 曾在链内全不可用时 `self.engines.iter().find(available)` 扫注册表兜底，会让 `argos`（`available()` 只要语言包在位即为 true，纯目录判断零网络）在**链外被抢先选中**，违反「在线优先、离线最后」。注意真正的降级执行 `translate_with_fallback_detailed:117-121` 本来就只按链顺序、**没有**这个问题。修：两端默认链补 `argos` 排末尾（在线优先 → 离线兜底）；`select()` 改为链内跳过不可用继续往后找、链内全不可用返回 `None`（无可用引擎由上层报错），并补 3 条单测固化语义（`select_respects_chain_order` / `select_does_not_fall_back_outside_chain` / `fallback_errors_when_all_chain_entries_unavailable`）。⚠️ 改 `select` 时若写成 `order.iter().find_map(|id| self.get(id)).filter(|e| e.available())` 会**取到链上第一个存在但不可用的引擎就返回 None**（不再往后找），单测 `select_respects_chain_order` 实测抓到了这个 bug——**过滤必须在 `find_map` 内部做**。 |

## 八、架构决策记录（ADR）

> 决策必须记录"为什么"，而不是只记"做了什么"。

### ADR-001：平台能力抽离（fs-platform）

- **状态**：Proposed（骨架已建，未接线）
- **背景**：fs-core 的截图/热键/托盘直接依赖 `windows` crate → 不可跨平台、core 单测连坐平台代码。
- **决策**：拆 `fs-platform`（trait + 纯逻辑）+ `fs-platform-windows`（Win32 实现），core 只依赖 trait。
- **后果**：core 可在 Linux/macOS CI 跑测；代价是多一层间接。可逆性高。

### ADR-002：本地服务化（fs-server daemon）

- **状态**：Proposed（依赖 ADR-001）
- **背景**：多端接入诉求（手机/平板/任意浏览器）。
- **决策**：不重写为服务，给 fs-core 增加第三个常驻进程 `fs-server`（127.0.0.1 本地 WS/gRPC）。协议复用 NM 契约。OCR 模型单实例常驻。
- **明确不做**：公网部署、多用户认证、云同步。

### ADR-003：引擎生态三层模型

- **状态**：Proposed
- **决策**：T1 内置引擎（编译期注册，覆盖 oar-ocr/local_llm）；T2 声明式 HTTP 引擎（JSON 描述符，覆盖 azure/google/openai_compat/mymemory）；T3 进程外插件（暂缓，复用 NM 协议）。
- **收益**：新增引擎从"改代码发版"降为"改 JSON 配置"。

### ADR-004：动作快捷键录入系统

- **状态**：Accepted（已实现）
- **背景**：原单一写死热键，三处默认值漂移（Ctrl+Alt+O / Alt+S / Alt+S），无法自定义。
- **决策**：`Config.hotkeys: HashMap<actionId, combo>` + `DEFAULT_HOTKEYS` + 旧字段迁移 + 多动作 `RegisterHotKey` 线程 + 保存热重载 + Settings `HotkeyRecorder`。
- **后果**：新增动作 = 加一行默认表 + 一个 on_trigger；用户自助重绑；保存即生效。

### ADR-005：桥接方案（withGlobalTauri 去留）

- **状态**：**Accepted（2026-09-29 实测验证）**
- **背景**：`withGlobalTauri` 曾与 `initialization_script` + `set_focus()` 组合触发 `0xcfffffff` 崩溃，被整体回退；但 `with_global_tauri` 默认 `false` → 前端桥接失效风险。
- **决策**：**采用方案 A——只加 `"withGlobalTauri": true`，不加 `initialization_script` / `set_focus`。**
  - 实测证据：tauri-dev17 运行 2 分钟+ 0 崩溃；`window.__TAURI__` 正常注入；前端 `invoke('ping')` 成功到达 Rust 命令（日志 `[BRIDGE_PROBE] ping invoked` 为铁证）。
- **后果**：
  - 变简单：窗口内按钮/快捷键桥接恢复，无需引入 `@tauri-apps/api` 依赖。
  - 变困难：`withGlobalTauri` 仍是曾与崩溃组合相关的变量，未来若再出现 `0xcfffffff`，需优先排查是否新增了与全局注入冲突的 `initialization_script` / `set_focus` 类配置。
  - 可逆性：高。删除该键即回到无全局注入状态（窗口内操作失效，但全局热键仍可用）。

### ADR-006：划词取词路径与 UIA 线程模型

- **状态**：**Accepted（2026-10-05 设计阶段定案）**
- **背景**：主程序需在任意桌面应用读取划选文本。候选路径：UIA `GetSelection()` / 剪贴板+合成 Ctrl+C / `WM_GETTEXT` / `GetGUIThreadInfo` / 截屏 OCR。
- **决策**：**三级降级—— UIA 为主路径，剪贴板合成 Ctrl+C 为兜底，截屏 OCR（复用 `region_picker`）为最终兜底。**
  - UIA 调用**全部**在一条**专用 MTA 线程**上（`CoInitializeEx(nullptr, COINIT_MULTITHREADED)`），该线程不拥有任何窗口。
  - 排除 `WM_GETTEXT` / `GetGUIThreadInfo`：前者是窗口级消息无"选区"概念、跨进程仅对内建 Win32 控件有效；后者只返回焦点句柄与插入符位置，均拿不到选中文本。
- **关键事实**：
  - **Chrome 138 起 Windows Chromium 默认启用原生 UIA**（官方博客 2025-08-14），「UIA 对 Chromium 支持差」已过时。本机 Edge 154，主力场景立即可用。
  - **必须用 MTA，不是 STA**。微软官方文档明确要求 MTA 线程；中文博客流传的"UIA 必须 STA"是误传。该线程"should not own any windows"。
  - `GetSelection()` 在无选区时返回 **NULL 而非空数组**，不判空会崩。
  - 剪贴板路径**不可盲目恢复原内容**：Office 等在剪贴板放指向内部数据的指针，覆盖后恢复会导致悬空崩溃。只读不恢复。
- **后果**：
  - 新增 Cargo features：`Win32_UI_Accessibility`、`Win32_System_Com`、`Win32_System_DataExchange`（已在 `windows-0.58.0` 核实存在）。
  - 不引入 `arboard`（项目已有 `windows` crate，剪贴板约 30 行，零新增依赖）。
  - 剪贴板路径会**覆盖用户剪贴板**，设置页需明示。
  - 详细设计见 `docs/划词取词设计.md`。
- **可逆性**：中。可将 UIA 降级为唯一剪贴板路径（覆盖面下降但代码更简单）。

### ADR-007：生词本最小字段集与复习算法推迟

- **状态**：**Accepted（2026-10-05 设计阶段定案）**
- **背景**：划词需沉淀为生词本。需决定字段范围与是否实现间隔重复复习（SM-2/艾宾浩斯）。
- **决策**：**M1 只做「收集 + 可搜索列表」，复习算法推迟到 M2；但建表时必须预留 `review_state` nullable 列。**
- **依据**：
  - 竞品核心洞察：沙拉查词存的是**「带语境的一句话」**（官网原文："每个单词的上下文亦被自动获取及翻译，珍贵的语境得到了保留"），故 `context` / `context_translation` 属essential 而非可选。
  - 复习算法外包：竞品的答案是导出到 Anki（沙拉查词官方支持 Anki 制卡），自研成本远高于对接。
  - 复习提醒是继"划词误触发"之后的**第二大用户骚扰源**（Chrome 商店真实评论），M1 不宜再加闹钟。
  - `review_state` 事后加列需改 schema + 数据迁移，代价远高于现在就多一列。
- **M1 明确不建字段**：`note` / `phonetic` / `definitions` / `example_sentences` / `tags` —— 避免滑向"大而全翻译工具"。
- **可逆性**：高。复习算法与词典字段均可后续 ALTER 加列实现。

### 10.5 构建注意事项（ct2rs / Argos 离线翻译）

- **⚠️ rsproxy.cn 镜像 ct2rs .crate 缓存残缺（P0，2026-10-04 确认）**：rsproxy.cn 镜像服务器上的 `ct2rs-0.10.1.crate` 缓存中，`CTranslate2/include/` 目录下所有 C++ 头文件丢失（807 个 `.h`/`.hpp` 缺失，含 `spdlog/version.h`、`cpu_features` 等），导致 MSVC `cl.exe` 报 `fatal error C1083: 无法打开包括文件: "ct2rs/include/config.h"`。**根因在 rsproxy 镜像服务器，非本机环境问题，非 Defender/杀软删除**。
  - **鉴别方法**：`tar tzf ~/.cargo/registry/cache/rsproxy.cn-*/ct2rs-0.10.1.crate | grep '\.h$' | wc -l` → 正常应 > 0，rsproxy 缓存实际为 0；同命令对 `index.crates.io-*` 副本应得 2229。
  - **修复**：`~/.cargo/config.toml` 注释掉 `replace-with = "rsproxy-sparse"`，回退 crates.io 官方源。官方源 `.crate` 含完整 4533 文件（2229 `.h` + 170 `.hpp`）。
  - **警告**：仅修复 `registry/src/` 目录**无效**——`cargo clean` 或重新构建时会从残缺 `.crate` 重新解压并覆盖修复。必须改 cargo config 切换源。
  - **当前状态**：`~/.cargo/config.toml` 已回退官方源并附注释，待 rsproxy 修复后再启用。：ct2rs 的 build script 会现场编译 CTranslate2 C++ 源码，依赖 **CMake ≥ 3.16**。`scripts/msvc-env.sh` 已内置存在性/版本检查，缺失即报错（建议 `winget install Kitware.CMake`）。
- **首次编译很长**：ct2rs 首次编译要拉取并编译 CTranslate2（含 oneDNN/OpenMP 等），**10~30 分钟属正常**；CI/门禁需预留超时，增量构建不受影响。建议用 `run_in_background` 跑首次 `cargo check`。
- **CTranslate2 源码需完整子模块**：`ct2rs` 的 path 依赖内含 `CTranslate2/`，其 `third_party/` 依赖 **spdlog（含 bundled fmt）、cpu_features、ruy → ruy/third_party/cpuinfo**（注意 cpuinfo 的正确源是 **`pytorch/cpuinfo`**，不是 `google/cpuinfo`）。同步子模块时**必须强制覆盖**：`robocopy /E /IS /IT`（用 `/XC /XN /XO` 只补缺失会留下新旧混搭，典型症状是 `common.h(168): error C2039: "basic_runtime": 不是 "fmt" 的成员`，因为 `fmt/bundled/core.h` 变成 192 字节的兼容 shim 而非真正的 fmt 8.1.1 核心）。
- **CRT 必须全局静态（`crt-static`）**：workspace 内 C++ 依赖对 CRT 的要求不一致——CTranslate2（CMake 硬编码 `MultiThreaded`）、`sentencepiece-sys`（跟随 `crt-static`）、`esaxx-rs`（来自 `lindera`/`oar-ocr` 日文分词，**无条件 /MT**）、`ort-sys`（ONNX Runtime）。混用 /MT 与 /MD 会报 **LNK2038 / LNK1319**（RuntimeLibrary 不匹配）与 **LNK1169**（`std::_Yarn<char>` 等符号重复）。解法：仓库根 `.cargo/config.toml` 统一 `[build] rustflags = ["-C", "target-feature=+crt-static"]`（**已落盘且需提交**），不要去改 `ct2rs/build.rs` 的 `static_crt` 或 CTranslate2 的 `CMakeLists.txt`。
- **protobuf 符号重复需开 `ort` 的 `load-dynamic`**：`sentencepiece-sys`（ct2rs 依赖）与 `ort-sys`（ONNX Runtime）各自静态编译了一份 protobuf，链接期报 **LNK2005 `google::protobuf::internal::*` + LNK1169**（`libort_sys` 342MB）。`ort` 的 default features 含 `download-binaries`（静态链接 onnxruntime.dll → 拖入 protobuf）而**不含 `load-dynamic`**。解法：workspace 增直接依赖 `ort = { default-features = false, features = ["std","ndarray","load-dynamic","download-binaries","copy-dylibs"] }`，`fs-core` 同步 `ort = { workspace = true }`（代码不直接调用其 API，仅统一 feature）。
- **⚠️ `load-dynamic` 必须配 `onnxruntime.dll`（P0，易漏）**：`ort-sys 2.0.0-rc.13` 起**不再分发 DLL**（其 `build/main.rs:28-29` 原注释："we don't need to download anything because **we don't provide DLLs anymore**"），`download-binaries` 只给静态 `onnxruntime.lib`。开 `load-dynamic` 即打开 `ort-sys` 的 `disable-linking`，转为**运行时 dlopen `onnxruntime.dll`**。
  - **影响面比预期大**：feature 是**全局统一**的，`load-dynamic` 经 `ort` → `oar-ocr` → `oar-ocr-core` 传导，**PP-OCRv6 的 OCR 推理也走动态加载**。缺 DLL 不是链接期错误，而是**运行时静默失败**，极难定位。
  - 解法：纯 Rust 工具 `cargo run -p fetch-onnx`（`--check` / `--force`，幂等；替代原 Python 脚本），已挂进 `scripts/build-all.sh`。`ORT_API_VERSION = 17`（`ort-sys/src/version.rs`，无 api-18+ feature）→ 需 ORT ≥ 1.18，工具固定 **1.23.0**。只取 `onnxruntime.dll` + `onnxruntime_providers_shared.dll`，**不要 DirectML**（项目零 `ort::` 调用，DML 仅 oar-ocr 可选 EP，见 `oar-ocr-core/src/core/config/onnx.rs:106`）。
  - 验收：`cargo run -p fetch-onnx -- --check` 通过，且 `target/debug/` 下有这两个 DLL。
- **诊断 CRT 混用的方法**：`/DEFAULTLIB:` 指令在 rlib 二进制中是明文 ASCII，可用 `re.finditer(rb"DEFAULTLIB:\"?([A-Za-z0-9_\-\.]+)", data)` 批量扫描，对比各 rlib 是 `LIBCMT/LIBCPMT`（/MT）还是 `MSVCRT/MSVCPRT`（/MD）。
- **运行期零依赖**：ct2rs 静态链接 CTranslate2，运行期无 Python、无外部动态库。
- **语言包获取**：第一版仅提供目录配置，用户手动放置语言包（可直接复制 Argos 安装目录 `packages/translate-*`）。语言包目录必须含 `model/`（`config.json` + `model.bin`）与平级 `sentencepiece.model`。
- **`▁`(U+2581) 必须自行 detokenize**：`ct2rs` 的 `SpTokenizer::decode` 走 `sentencepiece::decode_pieces`（纯词片拼接），**不做 SentencePiece 官方空白归一化**，空格标记 `▁` 会原样漏进译文。中文目标侧不产 `▁` 故 `en→zh` 正常，**英文等空格分词的目标语言必现**（`zh→en` 输出 `▁Patients▁need▁two▁weeks▁off.`）。`argos.rs` 的 `detokenize()` 负责 `▁`→空格 + 折叠连续空格 + 去首尾，**勿删**。
