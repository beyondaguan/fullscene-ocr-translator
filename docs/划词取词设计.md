## 一、问题定义与产品边界

### 1.1 要解决什么

用户在**任意桌面应用**（浏览器、Word、PDF 阅读器、聊天软件）里看到一段不懂的文字，需要在不打断阅读心流的前提下查到意思，并且**把这次查询沉淀下来**。

现有能力无法覆盖这个场景：
- 整屏/框选截图翻译需要**切换窗口 + 框选 + 等待 OCR**，打断心流；
- 扩展侧划词（`extension/src/content/hover-translator.ts`）依赖 DOM `Selection`，**只在浏览器进程内成立**。

### 1.2 明确不做（防止功能膨胀）

| 不做 | 理由 |
|---|---|
| 音标、词形变化、同反义词 | 词典展示能力，属"大而全翻译工具"，违背定位 |
| 间隔重复复习算法（SM-2/艾宾浩斯） | M1 只做「收集 + 可搜索列表」；复习外包给 Anki |
| 划词即生成例句 | 竞品沙拉查词的例句是**付费墙 + 每日 200 次限额**（官方 FAQ），说明例句是低频需求，划词即生成会拖慢主路径 |
| 自建语料库 / 词典 API 依赖 | 沙拉查词官方注意事项明写"双语例句受频率限制"。已配置 LLM（SiliconFlow/OpenAI）可按需生成，无需外部依赖 |
| WebView2 全屏透明浮窗 | 1.26 崩溃源，**永久禁止**。浮窗走纯 Win32 + GDI |

### 1.3 差异化

**「读 → 查 → 积累」闭环**。核心不是翻译，是**沉淀**：划词动作本身即记录，无需额外"收藏"操作。

竞品印证（沙拉查词官网原文）：「每个单词的上下文亦被自动获取及翻译，珍贵的语境得到了保留」——它存的不是"单词卡"，是**带语境的一句话**。这与本设计一致。

## 二、技术选型：取词双路径

### 2.1 结论

**UIA（UI Automation）为主路径 +剪贴板合成 Ctrl+C 为兜底 + 截屏 OCR 为最终兜底。**

### 2.2 三条路径对比

| 路径 | 覆盖面 | 实现代价 | 判定 |
|---|---|---|---|
| **UIA `GetSelection()`** | Word/记事本 ✅；**Chrome/Edge ✅（见 2.3）**；表格类部分；游戏/GPU渲染 ❌ | 中：2 个 feature + 专用 MTA 线程 + COM 生命周期 + 超时 | **主路径** |
| **剪贴板 + `SendInput`** | 所有响应 Ctrl+C 的应用（覆盖最广） | 低：1~2 个 feature + ~30 行 | **兜底** |
| **`WM_GETTEXT` / `GetGUIThreadInfo`** | 仅内建 Edit 类控件 | 低 | **排除**，见下|
| **截屏 OCR（复用 `region_picker`）** | 任何可见文字（含游戏、自绘控件） | 无新增（复用已有） | **最终兜底** |

**为什么排除 `WM_GETTEXT`**：它是**窗口级**消息，取的是控件全部文本，**没有"取选区"的概念**；且跨进程 `SendMessage` 只对内建 Win32 控件有效，对自绘/富文本/浏览器渲染完全无效——Chromium、Office 文档区、游戏都是自绘，控件根本不响应。

`GetGUIThreadInfo` 同理，只返回 `hwndFocus`（焦点句柄）和 `rcCaret`（插入符位置），**拿不到选中的文本范围**。

### 2.3 关键事实：Chromium UIA 已原生支持（推翻旧认知）

> **「UIA 对Chromium 支持差」这个流传已久的说法，在当前版本已过时。**

**Chrome 138 起，Windows 上的 Chromium 浏览器默认启用原生 UIA 支持**。Chromium 移除了中间的 MSAA→UIA 模拟层（原为 Windows 管理的"中间人"，带来延迟与可靠性问题），改为原生实现。官方点名 Voice Access 现在能在所有 Chromium 浏览器上正常工作。

- 来源：<https://developer.chrome.com/blog/windows-uia-support-update>（发布 2025-08-14）
- 本机验证：`C:\Program Files (x86)\Microsoft\Edge\Application\154.0.4258.53` —— **154 ≫ 138**，主力场景立即可用。
- 旧模式可用企业策略 `UiAutomationProviderEnabled` 回退，该策略支持至 Chrome 146。

⚠️ **遗留边界**：Chromium 仅为**已暴露到可访问性树**的文本节点提供 TextPattern。虚拟化列表、自定义 canvas 渲染的文字读不到，此时降级到剪贴板路径。

### 2.4 线程模型：必须 MTA，不是 STA

> ⚠️ **网上中文博客大量流传"UIA 必须 STA"，这是误传。实现时勿被误导。**

微软官方明确要求：

> "This thread should not own any windows, and **should be a Component Object Model (COM) Multi-threaded Apartment (MTA)** model thread (one that initializes COM by calling `CoInitializeEx` with the `COINIT_MULTITHREADED` flag)."
> — <https://docs.microsoft.com/zh-hk/windows/win32/winauto/uiauto-threading>

原因：UIA 基于 Windows 消息机制，跨线程调用需 MTA。

**实现要求**：
1. 单独开一条**专用 MTA 线程**（`CoInitializeEx(nullptr, COINIT_MULTITHREADED)`）
2. 该线程**不得拥有任何窗口**
3. UIA 调用**全部**在这条线程上（`GetFocusedElement`、`GetSelection`、`GetText`）
4. 线程内不跑消息循环，避免与主窗体冲突

### 2.5 必须处理的边界：`GetSelection()` 返回 NULL 而非空数组

微软 API 文档明确：当控件只支持插入点、或不支持文本选择时，`ranges` 被置为 **NULL**（不是长度 0 的数组）。

**不判空直接解引用会崩**。UIA 路径的降级触发条件：

```
ranges == NULL  →降级
ranges.Length() == 0  → 降级
拼接后文本 trim 后为空  → 降级
调用超时（建议 500ms）  → 降级
```

### 2.6 剪贴板路径的两个必知坑

**坑1：不能盲目恢复原剪贴板。** Office 等应用会在剪贴板中放入指向内部数据的指针。若覆盖剪贴板后原数据被释放，再"恢复"会导致指针悬空 → **应用崩溃**。

- 对策：借鉴 pot-app/Selection 的做法，**只读不恢复**。
- 影响：划词会覆盖用户剪贴板内容。这是本路径的已知代价，需在设置页说明。

**坑2：必须校验复制是否成功。** 用 `GetClipboardSequenceNumber()` 前后比对，序列号未变说明 Ctrl+C 没生效（目标应用不响应 WM_COPY），此时降级到截屏 OCR。

发送 Ctrl+C 前**必须先释放所有修饰键**（Ctrl/Alt/Shift/Space/CapsLock 等），否则可能与其他快捷键组合成意外行为。

### 2.7 依赖变更

根 `Cargo.toml` 的 `[workspace.dependencies.windows]` 需新增：

```toml
    "Win32_UI_Accessibility",     # IUIAutomation / IUIAutomationTextPattern
    "Win32_System_Com",           # CoInitializeEx / CoCreateInstance
    "Win32_System_DataExchange",  # OpenClipboard / GetClipboardData
```

**已验证这3 个 feature 名在 `windows-0.58.0/Cargo.toml` 中真实存在**（第709 / 595 / 607 行）。`Win32_System_Memory`（第 641 行）视 `GlobalLock` 需求再定。

**不引入 arboard crate**：项目已有 `windows` crate，直接用 `OpenClipboard` + `GlobalLock` 约 30 行，零新增依赖更符合项目一贯原则。

## 三、浮窗设计

### 3.1 技术形态：纯 Win32 + GDI 自绘

**复用 `crates/gui/src/window/region_picker.rs` 的既有模式**（`CreateWindowExW` + `WS_EX_TOPMOST | WS_EX_TOOLWINDOW | WS_POPUP`）。这是 1.26 崩溃后重建、**唯一经真机验证**的浮窗方案。

| 决策 | 理由 |
|---|---|
| 原生自绘，不用 WebView2 | 永久禁止（1.26 崩溃源） |
| 不用主窗口 | 浮窗必须能**在任意应用上方定位显示**，主窗体做不到 |
| 代价：无 `speechSynthesis` | TTS 需走独立通道，见 §5 |

### 3.2 交互状态机

移植 `extension/src/content/hover-translator.ts` 的 `selectionMode: 'button'` 逻辑（已成熟）。

```
[空闲]
   │ 选中文本（UIA 可读到选区）
   ▼
[小气泡出现]  ← 跟随光标定位，不抢焦点
   │ 用户点击气泡
   ▼
[翻译中]  → 走已有翻译引擎，秒级
   │
   ▼
[结果浮窗]
   ├─ 原文 + 译文
   ├─ [朗读] [收藏 ★] [详解] [×]
   └─ 详解展开 → 调 chat 生成例句/语法/用法

任意阶段：[×] 或 Esc → 回[空闲]
UIA/剪贴板均失败 → 浮窗给「框选取词」→ 复用 region_picker → OCR
```

**默认 button 模式**（选中不出浮窗，仅出现小气泡，点击才翻）。理由：竞品差评第一条就是「不想查词都会弹出，太容易触发了」。

### 3.3 收藏按钮的硬性要求

竞品最集中的差评是「添加生词按钮点上毫无反应」「这个怎么添加生词呢，没找到入口」。

**因此收藏按钮必须**：
1. **一眼可见**—— 浮窗底部常驻，**禁止藏右键菜单**
2. **点了立刻有反馈**—— 按钮态变化（实心★/已收藏）+ 可选 Toast
3. **永不失败** —— 写库失败要有可见提示，不能静默

### 3.4「详解」模块的开关设计

「平时可隐蔽」的具体落法：

| 条件 | 「详解」按钮 |
|---|---|
| 开关关闭（默认） | **不渲染** |
| 开关开+ 有 SiliconFlow/OpenAI 密钥 | 渲染，点击调 `chat` |
| 开关开 + 无密钥 | **静默不渲染**（不报错、不占位） |

依据：`chat()` 只走 `["siliconflow", "openai"]`（`crates/core/src/translate/mod.rs:127`），无密钥必然失败，渲染按钮等于给用户一个死按钮。

「详解」复用 AI 助手已验证的上下文注入模式（`shared-ui/src/main.tsx:392-419`：system 消息注入且不进可见历史）。

## 四、数据层设计

### 4.1 现状

`crates/core/src/database.rs:54` 仅有 `history` 一张表（`id / source / target / engine / created_at`）。**生词本从零建表**。

### 4.2 生词本表 DDL

```sql
CREATE TABLE IF NOT EXISTS wordbook (
    id                 INTEGER PRIMARY KEY AUTOINCREMENT,
    term               TEXT NOT NULL,           -- 选中的原文（词/词组/整句）
    translation        TEXT NOT NULL,           -- 译文
    context            TEXT,                    -- 划词时所在句子（可空）
    context_translation TEXT,                   -- 上下文译文
    engine             TEXT NOT NULL,           -- 实际出译文的引擎
    src_lang           TEXT NOT NULL DEFAULT 'auto',
    dst_lang           TEXT NOT NULL DEFAULT 'zh',
    source_app         TEXT,                    -- 来源应用进程名
    review_state       TEXT,                    -- 预留：SM-2 用，M1 恒 NULL
    created_at         TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_wordbook_created ON wordbook(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_wordbook_term    ON wordbook(term);
```

**字段取舍依据**：

| 字段 | 决策 | 理由 |
|---|---|---|
| `term` / `translation` / `engine` / `created_at` | Essential | 最小可用集 |
| `context` / `context_translation` | **Essential** | 竞品核心洞察：存的是"带语境的一句话"。缺了 context 生词本就退化成单词表|
| `src_lang` / `dst_lang` | Essential | 划词可能跨语言，缺了无法区分 |
| `source_app` | 建议存 | 成本极低，对"回溯当时在哪读的"有用 |
| `review_state` | **必须预留，恒 NULL** | 事后加 SQLite 列需改 schema + 数据迁移，代价远高于现在就多一列。将来上 SM-2 **零迁移** |
| `note` / `phonetic` / `definitions` / `example_sentences` / `tags` | **不建** | 违背 1.2 边界。`note` 可后续 ALTER 加，但 M1 不预建 |

### 4.3 `history` 与 `wordbook` 的关系

**划词同时写两张表**（用户明确要求"划词动作本身即记录"）：
- `history`：进入现有历史抽屉，语义 = "我翻译过什么"
- `wordbook`：进入生词本，语义 = "我收藏了哪个词块"

`wordbook` 是 `history` 的**子集视角**，通过 `term + created_at` 关联。**不做外键关联** —— 两者生命周期不同（历史可清空，生词本是长期资产），软关联更灵活。

### 4.4 `database.rs` 需扩展的接口

```rust
pub fn insert_word(&self, w: &WordEntry) -> Result<i64>
pub fn list_words(&self, limit: usize, query: Option<&str>) -> Result<Vec<WordEntry>>
pub fn delete_word(&self, id: i64) -> Result<()>          // 取消收藏
pub fn is_word_saved(&self, term: &str) -> Result<bool>   // 按钮态判断
```

`is_word_saved` 是 §3.3「点击立刻有反馈」的基础：浮窗显示前先查，★ 已是实心则表示已收藏。

## 五、TTS 设计：双实现适配层

### 5.1 为什么需要抽象层

**本机 Win10 Home 无 Speech FoD → OneCore Neural 不可用**。但代码可以先写好，将来装了 FoD 或换机即自动生效。因此做一层适配，按可用性自动降级，**不把 FoD 变成阻塞项**。

### 5.2 方案全景

| 方案 | 音质 | 本机现状 | Rust 可行性（已验证） | 判定 |
|---|---|---|---|---|
| **OneCore (Neural)** | 自然 | ❌ 无 FoD | ✅ `Media_SpeechSynthesis` feature 齐全：`SynthesizeTextToStreamAsync` / `SpeakingRate` / `AudioVolume` | 首选，探测不到音则不上线 |
| **SAPI5** | 机械 | ✅ **实测可用，中英文各 1 个** | ✅ `Win32_Media_Speech`：`ISpVoice` 完整 | **兜底（当前实际生效）** |
| WebView2 `speechSynthesis` | 依赖 Edge | ✅ | ✅ 已实现（`main.tsx:309`） | ⚠️ **仅主窗口可用，原生浮窗不可用** |
| edge-tts | 自然 | ✅ 需联网 | 需引入 Python/网络依赖 | 与"离线划词"冲突 |
| 离线 Neural 音 | 自然 | — | ❌ 微软仅对 Narrator 开放 | 第三方不可用 |

**SAPI5 与 OneCore 是两套独立系统**（注册表分别在 `Speech\Voices\Tokens` 与 `Speech_OneCore\Voices\Tokens`），不是同一套的不同版本。

在 WinOCR 项目上曾拒用 SAPIAdapter 桥接（为拿 Neural 音走 SAPI），**本项目不重演该做法** —— 划词要的是零依赖随叫随到，机械音可接受。

### 5.3 接口设计

```rust
pub trait TtsEngine: Send + Sync {
    fn voices(&self) -> Vec<VoiceInfo>;
    fn speak(&self, text: &str, opts: &TtsOptions) -> Result<()>;
    fn name(&self) -> &'static str;
}
pub struct TtsOptions { pub rate: f64, pub volume: f64 }

pub struct TtsRegistry { /* OneCore 优先，探测失败落 SAPI5 */ }
```

初始化流程：尝试 `SpeechSynthesizer::GetInstalledVoices()` → 成功则注册 OneCore；失败或无音则注册 SAPI5。**两者都不可用时，浮窗隐藏朗读按钮**（不报错）。

**语音选择规则**：按目标语言挑语音，`zh-*` → Huihui，其余 → Zira；无匹配则用默认语音。

### 5.4 本机实测结果（2026-10-05，用户执行验证）

```powershell
Get-ChildItem 'HKLM:\SOFTWARE\WOW6432Node\Microsoft\Speech\Voices\Tokens'
Get-ChildItem 'HKLM:\SOFTWARE\Microsoft\Speech\Voices\Tokens'
```

| Token | 名称 | 语言 |
|---|---|---|
| `TTS_MS_EN-US_ZIRA_11.0` | Microsoft Zira Desktop | en-US |
| `TTS_MS_ZH-CN_HUIHUI_11.0` | Microsoft Huihui Desktop | zh-CN |

**结论**：
- ✅ SAPI5 链路可用，**32 位与 64 位视图完全一致**（无 32/64 分歧风险）
- ✅ **中英文各 1 个** → 划词的「朗读原文」与「朗读译文」**两种场景都能覆盖**，不必等 OneCore
- 名称带 `Desktop` 后缀 → 确认属 SAPI5 语音（OneCore 语音不带此后缀）
- ⚠️ 音质为传统合成音（机械感明显）。**这是当前唯一实际生效的 TTS 通道**，
  OneCore 代码可先写好，待装FoD / 换机后自动生效。

> 附：验证 COM 层能否真正实例化（而非仅注册表有记录）用
> `Add-Type -AssemblyName System.Speech; (New-Object System.Speech.Synthesis.SpeechSynthesizer).GetInstalledVoices()`。
> 阶段 B3 真机跑浮窗时仍需确认一次 COM 初始化成功（`CoCreateInstance` 可能因 COM 单元状态失败）。

**COM 层实测（2026-10-05，同批执行）**：

```powershell
$s = New-Object System.Speech.Synthesis.SpeechSynthesizer
"可用语音数: " + $s.GetInstalledVoices().Count   # → 可用语音数: 2
$s.Speak('Hello, this is a test.')# → 无异常抛出
```

| 语音名 | Culture | 性别 |
|---|---|---|
| Microsoft Huihui Desktop | zh-CN | Female |
| Microsoft Zira Desktop | en-US | Female |

✅ **COM 初始化成功、`Speak()` 正常执行**（无HRESULT 异常）→ SAPI5 通道在本机**完全打通**，
阶段 A/B 的 TTS 部分**无任何阻塞项**。

⚠️ 实现注意：Rust 侧不走 `System.Speech`（那是 .NET 封装），直接用
`CoCreateInstance(SpVoice)` + `ISpVoice::Speak`。语音枚举同理用
`ISpVoice::GetVoices` + `ISpObjectToken::GetStringValue` 读 `'(default)'`。
两者对同一 COM 底层（`SAPI.SpVoice` / `SAPI5.dll`）操作，行为一致。

## 七、与扩展侧划词的边界

**不合并。** 二者是不同宿主环境的独立实现：

| | 扩展侧 | 主程序侧（本设计） |
|---|---|---|
| 取词机制 | DOM `Selection` | UIA / 剪贴板 / OCR |
| 运行环境 | 浏览器进程 | 任意 Windows 应用 |
| 浮窗技术 | Shadow DOM + WebView | 纯 Win32 + GDI |
| 复用关系 | 可共享 `hover-translator.ts` 的**状态机逻辑**；数据表可后续共享 | |

数据层统一的价值：用户在浏览器划的词和桌面划的词进同一个生词本。**但需等主程序 M3 完成后再评估**，当前不提前耦合。

## 八、遗留风险清单

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| 1 | ~~SAPI5 语音可用性~~ **已验证（§5.4）** | — | 注册表 + COM 层均确认可用，中英文各 1 音 |

## 九、决策记录

| 决策 | 选择 | 依据 |
|---|---|---|
| 取词路径 | UIA 优先 +剪贴板兜底 + OCR 终兜 | §2 |
| UIA 线程 | **MTA**（非 STA） | 微软官方文档，§2.4 |
| 触发方式 | button 模式（点击才翻） | 竞品差评第一条 |
| 例句生成 | 按需按钮触发，非划词即生成 | 竞品例句是付费墙+限额，证明低频 |
| 浮窗技术 | 纯 Win32 + GDI | 1.26 崩溃后唯一验证方案 |
| TTS | OneCore 优先 + SAPI5 兜底，适配层 | 本机无 FoD，但不能因此阻塞开发 |
| 复习算法 | M1 不做，仅预留 `review_state` 列 | 定位是沉淀非训练；外包给 Anki |
| 详情字段 | M1 不建音标/词形/同反义 | 避免大而全 |

**新增 ADR 建议**：ADR-006（UIA 取词路径与 MTA 线程模型）、ADR-007（生词本最小字段集与复习算法推迟）。实施时补入规范 §八。
